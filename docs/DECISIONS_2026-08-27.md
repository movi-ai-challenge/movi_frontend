# MOVI 2026-08-27 확정 결정

> 결정일: 2026-08-27, Asia/Seoul
>
> 내부 완료 목표: 2026-09-02
>
> 상태: 팀 실행 기준으로 확정

## 문서 효력

이 문서는 2026-08-27에 검토한 조사·권장안을 팀 결정으로 확정한 기록이다. 기존 문서와 충돌하면 이 문서를 우선한다.

여기서 확정한 것은 제품 범위, 안전 정책, 우선순위와 채택 게이트다. 원문에 없던 endpoint, DTO 필드명, 환경 URL, WebSocket 인증 방식과 배포 secret은 확정된 것으로 간주하지 않으며 구현 전에 담당 팀이 상세 계약으로 기록한다.

## 목표와 일정

- 경쟁력의 중심은 불완전한 음성 보완, 거래 재확인, 위험 거래 차단, 비음성 업무 완료다.
- 2026-09-02는 사용자가 기존 계획에 이틀을 더해 정한 내부 목표이며, 대회 공식 마감 연장을 뜻하지 않는다.
- 2026-08-30 기능 동결, 8월 31일 회귀 검증, 9월 1일 사용자·모델 평가와 리허설, 9월 2일 최종 버퍼를 적용한다.
- 9월 1~2일에는 미구현 기능을 새로 추가하지 않는다.
- 실제 AI 계약과 금융 안전 검증을 우선하고, 용량이 부족하면 적금·미등록 계좌·실제 SMS를 제외하며 Streaming은 multipart fallback으로 내린다.

## P0 확정 범위

### 실제 AI Voice/FDS

- 실제 AI Schema, 예제, 버전과 실행 환경을 확보한 뒤 연동한다.
- AI intent `transfer_money`, `check_balance`, `check_history`, `confirm`, `deny`, `cancel`, `unknown`을 Backend Adapter에서 기존 도메인 명령으로 변환한다.
- `deny`는 현재 거래 승인 취소 후 수정, `cancel`은 전체 흐름 취소로 구분한다.
- AI Context는 언어 해석에만 사용하고 수취인·금액·확인 상태는 백엔드 검증 결과만 신뢰한다.
- FDS 원본 점수는 0~100 의미와 정책 버전을 보존한다. 프런트는 이를 사기 확률로 표현하거나 기존 0~1 점수로 임의 환산하지 않는다.
- `HIGH`와 `CRITICAL`은 모두 `BLOCK`이며 추가 인증으로 해제하지 않는다.
- FDS timeout, 장애와 잘못된 payload는 fail-closed로 처리한다.

### OpenBanking과 인증 복귀

- 결과 URL은 `result=success` 또는 `result=error&error=...` 형식을 유지한다.
- OpenBanking callback GET만 공개하고 `state`의 소유권, 일회성, 만료와 재사용을 검증한다.
- 성공·취소·오류는 모두 고정 프런트 callback URL로 302 복귀한다.
- URL에 토큰, 인가 코드와 계좌 정보를 남기지 않는다.
- 카카오 교환 코드 배포 확인 후 legacy token query 호환 모드를 종료한다.
- 기존 AWS 배포 파이프라인을 사용하며 새 NCP 이전 작업을 만들지 않는다.

### 거래 확인과 PIN 재인증

- 일회용 확인 코드는 거래 의사 확인이며 본인 인증 수단이 아니다.
- 확인 코드는 서버 생성 6자리 무작위 숫자, 60초, 1회 사용, 최대 3회로 한다.
- 금액, 수취인 또는 출금 계좌가 바뀌면 `confirmationId`, 확인 코드와 `reauthProof`를 모두 폐기한다.
- MVP 재인증은 기존 PIN 검증을 재사용한 거래 바인딩 proof 하나로 제한한다.
- PIN을 음성으로 말하게 하지 않는다.
- 재인증이 필요한 거래는 유효한 proof가 없으면 실행하지 않는다.
- 생체인증과 Passkey는 이번 제출 범위에서 제외한다.

### 비음성 직접 입력 송금

- 최소 직접 입력 송금 완료 경로를 P0 핵심 범위에 포함한다.
- 등록된 수취인 선택, 출금 계좌와 금액 입력, 서버 검토, 명시적 최종 확인, 필요한 PIN 재인증, 멱등 실행 순서로 구성한다.
- 기존 한도, FDS, 상태 조회와 보호자 이벤트 실행 계층을 재사용한다.
- 가짜 음성 파일, STT confidence와 신뢰 기기 값을 생성하지 않는다.
- 입력 채널과 비음성 FDS 피처의 `null` 또는 해당 없음 의미를 AI·백엔드 계약에 명시한다.
- 검토 전용 화면은 비음성 송금 완료로 발표하지 않는다.

### 안전성 증거

- 같은 멱등성 키의 동시 요청에도 외부 이체와 Transfer는 각각 1건이어야 한다.
- 확인 전, 확인 코드 불일치, 거래 변경, `HIGH`·`CRITICAL`, FDS 장애에서는 이체가 0건이어야 한다.
- 실행 응답 유실 후 같은 키로 최종 상태를 복구하고 새 키를 자동 생성하지 않는다.
- 은행 성공 후 응답 유실 상태를 일반 실패와 분리하며, 불명확한 상태에서 새 송금을 유도하지 않는다.
- SMS 실패가 완료된 송금을 되돌리지 않는다.

## P1 채택 게이트

### 제한 Streaming

- 인증된 Backend WebSocket을 통한 한 세션·한 발화 Streaming을 우선 구현한다.
- interim은 화면 표시만 하고 금융 처리에는 final만 사용한다.
- 인증, 세션 소유권, chunk 순서·크기·총 길이, 중복 final, 끊김과 timeout을 검증한다.
- 장기 JWT를 WebSocket URL query에 넣지 않는다. 정확한 인증 방식은 상세 계약으로 확정한다.
- 2026-08-29까지 프런트·백엔드·AI 실연동과 안전 테스트를 통과한 경우에만 기본 경로로 채택한다.
- 게이트를 통과하지 못하면 multipart를 시연 기본 경로로 유지한다.
- 실행 요청 이후 오류에서는 오디오 재전송보다 동일 멱등성 키 상태 조회를 먼저 수행한다.

### MP4와 모바일

- 백엔드 MP4 PR #92, 프런트 MIME·확장자, AI 실제 디코딩을 함께 검증한다.
- multipart MP4와 Streaming 오디오 형식은 별도 계약으로 취급한다.
- 2026-08-30까지 iOS 실기기 녹음과 디코딩을 통과해야 지원 완료로 표시한다.

### 접근성 설정과 읽기

- 고대비, 큰 글씨와 단순 모드만 기기 `localStorage`에 저장한다.
- 금융·인증 정보는 접근성 설정 저장소에 저장하지 않는다.
- 읽기는 서버 `voiceMessage`와 현재 화면의 허용된 문구를 사용한다.
- PIN, 토큰, 숨겨진 DOM과 원문 금융정보를 AI에 보내지 않는다.
- Google TTS 신규 연동은 제외하고 브라우저 TTS, 화면 텍스트, 다시 듣기와 키보드 조작을 유지한다.

### 자동화

- Playwright는 로그인·조회·음성 송금 복구의 핵심 흐름에 한정해 도입한다.
- Testing Library 전체 전환은 후순위다.
- 실제 staging E2E는 자동화 도입을 기다리지 않는다.
- 새 개발 의존성을 설치할 때는 저장소 규칙에 따라 별도 승인을 받는다.

## 이번 제출 제외

- 적금 조회
- 준비된 Sandbox 검증 계약이 없는 미등록 계좌번호 송금
- 실제 SMS 연동 전환
- 보호자 승인, 대시보드와 공개 링크
- 생체인증과 Passkey
- SHAP 화면
- 새 디자인 전면 개편
- 새 배포 시스템 또는 인프라 이전

등록 수취인 정보와 입력 계좌 정보가 불일치하면 거래를 거부한다. 임의 문자열 매칭은 사용하지 않는다.

## 아직 필요한 상세 계약

다음은 범위가 아니라 구현에 필요한 구체 값이 남은 항목이다.

- 실제 AI Voice/FDS endpoint, health/version, Schema, fixture, timeout과 정책 버전
- Intent·Entity Adapter 필드와 오류 매핑
- Streaming WebSocket endpoint, 인증 방식, chunk·timeout 제한
- 등록 수취인 목록, 직접 입력 검토·실행, 확인 코드와 PIN proof endpoint·DTO·오류 코드
- 입력 채널과 비음성 FDS 피처의 null/해당 없음 표현
- OpenBanking 환경별 origin·redirect URI와 비민감 오류 식별자 목록
- 신규·비신뢰 기기, 신규 수취인과 금액·세션 경과에 따른 PIN proof 요구 조건
- 은행 성공 후 응답 유실의 거래 식별자와 결과 조회 계약

상세 계약이 없다는 이유로 확정된 제품 범위를 다시 `합의 필요`로 돌리지 않는다. 반대로 제품 범위가 확정됐다는 이유로 endpoint나 보안 필드를 프런트가 임의로 만들지 않는다.
