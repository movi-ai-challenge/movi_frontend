# MOVI MVP 프론트엔드 1주일 구현 계획

> 2026-08-24 요구사항 변경: 보호자는 금융 정보 조회나 이체 승인 권한을 갖지 않고 위험 거래 알림만 받는다. 세부 정책은 [GUARDIAN_ALERT_POLICY.md](GUARDIAN_ALERT_POLICY.md)를 따른다.

## 목표

첨부된 `MVP 기능명세서`에 적힌 기능만 사용하여, 백엔드 없이도 Mock 데이터로 핵심 사용자 흐름을 시연할 수 있는 접근성 중심 웹앱 목업을 완성한다.

완료 시 다음 흐름을 키보드, 터치, 화면 읽기 프로그램, 음성 UI의 대체 입력으로 수행할 수 있어야 한다.

1. 로그인 후 오픈뱅킹 계좌 연결 및 기본 계좌 설정
2. 음성 또는 직접 입력으로 잔액과 거래내역 조회
3. 수취인과 금액을 입력하고 이체 내용을 최종 확인
4. FDS 위험 거래 감지 결과와 보호자 알림 상태 확인
5. 이체 결과 확인 및 음성 안내 반복
6. 보호자 알림 연락처 연결과 위험 거래 알림 흐름 시연

## 명세 기반 기능 범위

### 인증

- 회원가입 및 비밀번호 또는 카카오 로그인
- PIN 또는 생체인증 로그인
- 로그아웃

목업에서는 실제 OAuth와 생체인증을 구현하지 않고 명세 흐름을 Mock으로 시연한다. 인증 방식과 API 계약은 백엔드 합의 전까지 확정하지 않는다.

### 오픈뱅킹

- 1.1 계좌 연결 시작
- 1.2 계좌 등록
- 1.3 연결 계좌 조회
- 1.4 기본 계좌 설정
- 1.5 계좌 연결 해제
- 1.6 인증 만료, 인증 오류, 통신 오류와 재시도 안내
- 1.7 Sandbox 또는 Mock 계좌와 거래 데이터

### 음성 인터페이스와 재질문

- 음성 녹음 및 음성 파일 전송 상태
- STT 변환 결과 표시
- 명령 의도와 금융 정보 추출 결과 표시
- 진행 상황과 실행 전 재확인 음성 응답
- 낮은 인식률 감지와 보완 질문
- 금액 누락 시 재질문
- 수취인 누락 시 재질문
- 다중 후보 처리
- 재질문 중 기존 금액과 수취인 유지
- 연속 실패 시 직접 입력으로 전환

실제 Google STT/TTS, RASA, SpaCy 연동은 프론트엔드 목업 범위가 아니다. 프론트엔드는 해당 API의 상태와 결과를 Mock으로 표현한다.

### 잔액조회

- 기본 또는 지정 계좌 선택

- 계좌번호 마스킹

## 일자별 실행 계획

### Day 1 - 명세 추적 구조와 접근성 기반

- 명세 기능 ID와 화면/상태의 연결표 확정
- 전체 P0 라우트 뼈대 구성
- 사용자 화면과 보호자 알림 링크 흐름 구분
- 고대비, 큰 글씨, 단순 화면 모드 상태 설계
- 공통 버튼, 입력, 오류, 상태 안내, 다이얼로그의 접근성 계약 정의
- Mock Seed 데이터 확장

완료 조건: 모든 P0 기능이 어느 화면과 상태에서 시연되는지 추적 가능해야 한다.

### Day 2 - 인증과 오픈뱅킹

- Mock 로그인/로그아웃
- 계좌 연결 동의 및 Sandbox 연결 상태
- 계좌 목록과 기본 계좌 설정
- 인증 만료, 연결 실패, 재시도
- 잔액 표시, 마스킹, 다시 듣기

완료 조건: 키보드와 화면 읽기 프로그램으로 로그인부터 잔액 확인까지 진행 가능해야 한다.

### Day 3 - 음성 인터페이스와 재질문

- idle, listening, processing, speaking, error 상태
- STT 결과 확인 및 수정
- 수취인 또는 금액 누락 재질문
- 앞서 입력한 정보 유지
- 다중 후보 선택
- 반복 실패 시 직접 입력 전환

완료 조건: 마이크가 없어도 동일한 기능을 직접 입력과 키보드로 완료할 수 있어야 한다.

### Day 4 - 이체와 FDS

- 등록 수취인 조회
- 수취인 및 금액 입력
- 최종 확인 및 음성 확인/취소 상태
- FDS 평가 중 상태
- 저위험 즉시 이체
- 위험 거래 감지와 보호자 알림 요청
- 위험 거래 처리와 차단 규칙은 `확인 필요`
- 중복 제출 방지와 성공/실패 결과

완료 조건: 세 위험도 시나리오가 분명히 다르게 동작하고, 명시적 확인 없이 거래가 완료되지 않아야 한다.

### Day 5 - 거래내역, 보호자 연결, 알림

- 최근 거래, 기간, 유형 필터와 거래 상세
- 거래내역 음성 안내
- 보호자 전화번호 입력과 연결 요청
- 보호자 알림 연락처 연결 상태
- 이체 완료 알림과 위험 거래 긴급 알림
- 알림에서 마스킹된 위험 거래 정보로 이동

완료 조건: 위험 거래 감지에서 보호자 알림 발송 결과까지 목업 흐름이 이어지고, 보호자에게 금융 조회나 승인 권한이 없어야 한다.

### Day 6 - 접근성 및 사용성 집중 QA

- 고대비, 큰 글씨, 단순 화면 모드 검증
- 키보드 전체 흐름과 포커스 이동 검증
- 화면 읽기 프로그램의 제목, 레이블, 상태 읽기 검증
- 200% 확대와 모바일 reflow 검증
- 오류 음성 안내와 시각적 대체 안내 검증
- VoiceOver 또는 동등한 화면 읽기 프로그램으로 P0 세 흐름 검증

완료 조건: 접근성 완료 기준을 만족하지 못한 P0 화면이 없어야 한다.

### Day 7 - E2E 안정화와 시연 준비

- 명세 12.8 전체 Mock E2E 흐름 검증
- 정상 거래와 보호자 알림 대상 위험 거래 Seed 시나리오 고정
- lint, typecheck, build
- 콘솔 오류와 막힌 경로 제거
- 팀 실행 방법과 알려진 제한사항 문서화

완료 조건: 새로 실행한 환경에서 핵심 시연을 중단 없이 반복할 수 있어야 한다.

## 명세 추적 규칙

각 구현 작업과 커밋에는 가능한 경우 명세 번호를 적는다. 예: `5.3 이체 정보 확인`, `11.4 키보드 조작`.

커밋은 하나의 기능 또는 하나의 화면 단위로 구성한다. 공통 기반, 설정, 문서 변경은 기능 구현과 별도 커밋으로 분리한다. 커밋 전에는 staged diff를 확인해 관련 없는 파일과 미완성 작업이 섞이지 않았는지 검토한다.

커밋 메시지 예시는 다음과 같다.

- `Implement 1.3 connected account list`
- `Implement 5.3 transfer review screen`
- `Add 11.1 high contrast theme`
- `Document MVP implementation plan`

기능 완료 보고는 다음 형식을 사용한다.

| 명세 항목 | 구현 화면/컴포넌트 | Mock/API | 접근성 검증 | 상태 |
|---|---|---|---|---|
| 5.3 이체 정보 확인 | 확인 필요 | Mock | 미검증 | 대기 |

명세에서 근거를 찾지 못한 요청은 구현하지 않고 `범위 밖`으로 보고한다.

- 비밀번호, 카카오, PIN, 생체인증 중 실제 MVP 시연 방식

- STT/TTS 요청 형식과 스트리밍 여부
- FDS 위험도 값과 위험 사유 응답 형식
- 보호자 알림을 발생시키는 FDS 위험 등급
- 보호자 알림과 독립적인 위험 거래 실행·보류·차단 규칙
- 보호자 알림 채널, 링크, 인증 및 만료 방식
- 거래 및 알림 API 응답 타입
- 고대비, 큰 글씨, 단순 화면 모드의 사용자별 저장 방식
